# AGENTS.md — 项目工程纪律（v4 · 研发范式）

本文件定义项目级通用工程约束。8 个 `rd-*` Skill 可**独立使用、任意顺序执行**，不强制流水线。

---

## 动手前——先想清楚再动手

- 明确陈述你的假设。如果不确定，先问。
- 如果存在多种理解方式，列出来让用户选。
- 如果存在更简单的方案，主动说。该反驳时反驳。
- 先读目标文件，再读调用方、接口定义、相关测试、配置和数据模型。
- 如果影响多个模块或对外契约，先给出简短实施计划。

## 最小改动原则

- 优先最小必要改动，不顺手重构无关代码。
- 优先复用现有模式、目录结构和基础设施。
- 不因为"以后可能会扩展"而提前增加抽象层。
- 不"改善"相邻代码、注释或格式；只改该改的。
- 你的改动导致的孤立代码由你清理；已有的不动。
- 每一行改动都应能追溯到用户的需求。

## 目标驱动执行

将任务转化为可验证目标：
- "加验证" → "写无效输入的测试，然后让测试通过"
- "修 bug" → "写复现测试，然后让测试通过"
- "重构 X" → "确保重构前后测试都通过"
- 运行 lint、format、test、build、typecheck 前，先查项目已有脚本入口，如 `scripts/`、`script/`、`package.json`、`Makefile`、`justfile`、`pyproject.toml`、`uv.lock`。优先使用项目封装命令，不绕过本地约定直接调用底层工具。

## 何时直接做 / 何时先问

| 判断 | 行为 |
|------|------|
| 指令明确，改动可控 | 直接做 |
| 多种合理方案且影响不同 | 给出推荐 + 理由，问用户选哪个 |
| 需求模糊 | 先复述理解，确认后再做 |
| 破坏性操作（删文件/改架构/数据库变更） | **必须先确认** |
| 不确定能否做到 | 先说明风险和限制，不承诺后失败 |
| 需要创建多个新文件或目录 | 先告知计划和文件清单；影响架构/契约或破坏性操作时再确认 |
| 用户给出模糊需求，需要先结构化 | 引导用户澄清，不替用户做关键业务决定 |
| 研究任务涉及不确定领域 | 先搜索核实，再给结论 |
| 复杂多步任务或大范围重构 | 先用 `/plan` 模式制定计划 |
| 多个独立子任务可并行 | 使用 Codex 子代理并行执行 |

## 质量门禁底线

研究、设计、实现、评审类任务完成前，至少确认：

- 关键结论有证据支撑，而不是只基于推断。
- 关键假设已显式标注。
- 失败路径和边界条件已覆盖。
- 无法确认的点已单独列出。
- 验证动作和验证结果已记录。

## 规范注入（Spec Injection）

借鉴 Trellis 的规范自动注入模式：项目级规范存储在仓库中，每次会话自动加载，确保 AI 行为与项目约定一致。

### 规范层级

| 层级 | 载体 | 加载方式 |
|------|------|---------|
| 全局规范 | `~/.codex/AGENTS.md` | 每次会话自动加载 |
| 项目规范 | 项目根 `AGENTS.md`（本文件） | 每次会话自动加载 |
| 模块规范 | 子目录 `AGENTS.override.md` | 进入该目录时加载 |
| 跨会话记忆 | Codex 内置 Memories | 自动提取和注入 |

### 规范检查要求

涉及设计和实现的 Skill（`$rd-technical-writing`、`$rd-detailed-design`、`$rd-implement`、`$rd-code-review`）执行前：
1. 检查项目根是否有 `AGENTS.md` / `AGENTS.override.md` 中的项目特定约定
2. 检查是否有已固化的设计决策或架构约束
3. 新的设计决策建议通过 Codex Memories 或 AGENTS.md 持久化

### 规范维护要求

- `AGENTS.md` 面向 agent，记录工程约束、脚本、目录约定、风险点和验证命令；`README.md` 面向人类，说明项目是什么、为什么存在、如何开始。不要在两者之间复制同一段内容，必要时互相链接。
- 修改 AGENTS.md 前先搜索是否已有等价规则。优先收紧已有规则，不重复新增。
- 当 AGENTS.md 已明显变长时，新增规则必须同时评估是否有过期、重复或不可执行规则应删除或合并。
- Skill frontmatter 的 `description` 是触发摘要，必须先写触发条件，保留最短可检索长度。优先写适用场景、症状和边界，不写宣传语、内部流程或价值判断。

## 人机协作模式

根据任务类型选择合适的协作模式：

| 模式 | 适用场景 | 人工投入 | AI 贡献 |
|------|---------|---------|--------|
| **AI First** | CRUD、标准化功能、脚手架生成、文档模板填充 | 20%（审核） | 80% |
| **Human First** | 复杂业务逻辑、核心算法、架构决策 | 70%（设计） | 30%（辅助） |
| **Pair Mode** | 重构、调试、学习新技术、探索性原型 | 50% | 50% |

选择指南：不确定时默认 Pair Mode。AI First 的前提是任务边界清晰且有验证手段。

## Hooks 确定性保障

> **原则**：需要每次都执行的事情用 Hooks，不要靠 prompt 提醒。Hooks 是确定性的，Skills 是概率性的。

### 推荐 Hooks 配置

| 触发点 | 用途 | 示例 |
|--------|------|------|
| **PostToolUse（Write）** | 写文件后自动 lint/format | `npm run lint:fix` |
| **PreCommit** | 提交前检查 secrets 泄露 | 扫描 `.env` / `.key` / `.pem` |
| **Stop** | 会话结束时记录摘要 | 输出新发现的约定到日志 |

具体配置见 `config.toml` 中的 `[hooks]` 部分。

- 不得绕过 pre-commit / pre-push hooks。除非用户明确授权，禁止使用 `--no-verify` 或等价参数。

## 代码库地图

大型项目（>50 个顶层目录或 >10 万行代码）必须在项目根目录维护一份 `CODEBASE.md` 地图：

```
# 代码库地图
## 核心服务
- services/api/       — REST API 网关
- services/payments/  — 支付处理
## 共享库
- packages/types/     — 跨服务类型定义
## 不要碰
- generated/          — 自动生成，不要手动修改
```

地图只描述最高层结构；子目录细节放对应的 `AGENTS.override.md`。

## 噪音排除

生成文件、构建产物、第三方代码不应出现在 AI 的搜索范围中：

- 在 `.gitignore` 或 `.ignore` 中排除 `node_modules/`、`dist/`、`build/`、`vendor/`、`generated/`
- 对于 Codex CLI，可在 config.toml 中配置排除规则
- 排除规则提交进版本库，整个团队共享

## 上下文管理与会话策略

对抗长会话中的上下文丢失：

- 实施计划中包含**完整文件路径**（即使模型忘了上下文也能重新定位）
- 复杂多步任务开始前，先摘要当前上下文中的关键约束
- 善用 Codex Memories 将关键决策持久化

### 会话刷新策略

大型任务推荐拆分为多个独立会话：

| 会话 | 目标 | 持久化 |
|------|------|--------|
| 会话 1 | 理解代码库结构和约束 | 关键发现写入 AGENTS.md 或 Memories |
| 会话 2 | 基于 AGENTS.md 实现功能 | 代码提交到 Git |
| 会话 3 | 独立验证和测试 | 测试结果记录 |

### 何时开新会话

- 回答质量明显下降（重复之前的错误、遗忘关键约束）
- **两次失败规则**：同一问题连续两次修复失败 → 开新会话 + `git reset --hard`，从干净状态重新开始（上下文已被污染）
- 任务类型切换（如从需求分析切到代码实现）
- 上下文被压缩 2 次以上

## 配置迭代原则

每 3-6 个月或大版本模型发布后做一次配置 review：

- 区分两类规则：**弥补模型局限**的规则（应随模型升级重新评估） vs **项目固有约定**的规则（长期有效）
- 过时的限制性规则会约束新模型能力（如"每次只改一个文件"在新模型上可能是负优化）
- 清理过期配置和写新配置一样重要

## 需求分析约束

- 不跳过需求澄清直接进入设计或实现。
- 区分用户原始表述和结构化需求；保留原始表述，不篡改用户意图。
- 区分功能需求、非功能需求、约束条件和假设。
- 需求必须可验证；每条需求至少对应一种验证方式。
- 优先级必须显式标注。
- 避免无定义的歧义动词（如"支持""处理""优化"）。
- 避免无指标的主观描述（如"响应快""稳定""美观"）。
- 涉及多角色、多场景时，角色和场景必须枚举。

完整工作流见 `$rd-requirements-analysis` skill。

## 先搜索，再构建

1. 搜索 `{runtime} {thing} built-in`
2. 搜索 `{thing} best practice {current year}`
3. 查阅官方文档

## 证据纪律

- 能用代码确认的，优先看代码
- 能用官方文档确认的，优先看官方文档
- 能用标准 / RFC / 论文确认的，优先看原始来源
- 如果外部能力不可用，必须明确说明"当前无法独立核实"

## MCP 工具路由

根据问题类型选择合适工具，不要滥用：

- **库/框架/SDK 文档**：优先 Context7
- **大型开源项目架构**：DeepWiki（按需启用）
- **多方案比较/复杂推理**：Sequential Thinking（按需启用）
- **Web 搜索**：Codex 内置 `web_search` 为主；只有在 MCP 服务器已配置、凭据有效且已启用时，才使用 Tavily 或 Brave Search
- **浏览器交互/E2E 测试**：优先内置浏览器工具或 Playwright CLI；Playwright MCP 按需启用
- **跨仓库代码分析**：Augment Context Engine MCP（按需启用）

## 学术与标准检索

当任务需要论文、技术标准、RFC 或行业规范时：

- 优先使用英文关键词构造搜索查询。
- 标准/规范优先查官方来源，如 NIST、ISO、IEC、IETF、厂商官方文档。
- 对时效性主题限定年份，并标注来源发布时间。
- 权威标准或官方规范的原文条款可作为主证据；争议性、非官方或影响方案取舍的关键结论，尽量交叉验证 2-3 个来源，无法交叉验证时降低置信度。

## 证据分级

1. 代码 / 系统实际行为
2. 官方文档 / 标准 / RFC
3. 论文 / 技术报告
4. 工程实践文章
5. 明确标注的推断

## 质量门禁

### 需求分析（`$rd-requirements-analysis`）
- 核心场景已覆盖、需求可验证、优先级已标注、排除项已明确

### 需求评审（`$rd-doc-review` 需求评审模式）
- 完整性、可验证性、一致性、优先级合理性、边界清晰度检查完成

### 技术方案 / 概要设计 / 建设方案（`$rd-technical-writing`）
- 候选方案比较充分（≥2 个）、推荐依据明确、风险与回滚已说明
- 建设方案含部署架构设计（拓扑、环境、策略、容量）

### 方案评审（`$rd-doc-review` 方案评审模式）
- 需求覆盖、架构合理性、部署架构、成本、风险检查完成

### 详细设计（`$rd-detailed-design`）
- 接口/数据模型/关键流程/失败路径/并发要求明确

### 设计评审（`$rd-doc-review` 设计评审模式）
- 接口完备性、数据模型、并发控制、安全设计、可实现性检查完成

### 代码实现（`$rd-implement`）
- 代码符合设计、核心功能有测试、无硬编码 secrets

### 代码评审（`$rd-code-review`）
- 双阶段：合规性检查通过 → 质量深度评审完成、问题已分级

### 测试（`$rd-testing`）
- 正常/异常/边界条件覆盖、结果已记录、失败用例有根因分析

### 部署（`$rd-deployment`）
- 操作手册可重复、回滚方案存在、部署后验证通过

## 详细设计约束

- 详细设计不应只写抽象原则，必须下沉到接口、数据、流程和错误路径。
- 如果前置技术方案不存在，可基于当前问题直接产出详细设计，但要明确假设。
- 对关键边界条件、失败路径、并发场景必须显式说明。
- 涉及 AI/ML 系统时，必须包含评估设计、数据边界和降级策略。

---

## 核心实现约束

- 优先最小可行改动，优先复用现有模式。
- 库/框架用法不确定时，优先通过 Context7 或官方文档核实。
- 如果无法独立核实，不要把猜测写成实现依据。
- 引入新依赖前确认版本、许可证和已知安全漏洞。
- 不把过程草稿、任务日志、分析报告默认写进仓库。
- 重命名函数、类型、文件、Skill、MCP 工具名或配置键时，分别检查直接引用、类型引用、字符串字面量、动态导入、re-export / barrel 文件、测试与 mock。一次搜索不足以证明无遗漏。

### 代码质量阈值

| 约束 | 阈值 |
|------|------|
| 单个函数/方法 | ≤ 50 行 |
| 单个文件 | ≤ 500 行 |
| 嵌套层级 | ≤ 3 层 |
| 函数参数 | ≤ 5 个 |
| 注释 | 解释 WHY 而非 WHAT |

### 过度设计判断

- 当前只有 1 个实现 → 不建接口/抽象工厂
- 当前没有变化需求 → 不用策略模式/模板方法
- 消除重复会引入更高复杂度 → 保留适度重复

## 安全性设计约束

安全性是通用软件工程的基本质量属性，在设计和实现阶段默认考虑：

- 身份认证与授权：认证方式选型、最小权限原则、会话管理
- 输入校验：所有外部输入必须校验
- 数据保护：敏感数据加密传输和存储、日志脱敏
- 审计与追踪：关键操作留审计日志
- 依赖安全：引入新依赖前确认版本和已知漏洞
- 失效处理：异常不泄露内部信息

### 高风险场景

以下场景必须更保守，默认需要额外验证或复核：

- 认证、授权、会话、JWT、OAuth。
- 数据库迁移、删除、批量更新。
- 文件上传、模板渲染、命令执行。
- 支付、订单、账务。
- Webhook、外部回调、跨租户数据。
- token、密钥、证书、secrets。

安全性设计融入 `$rd-technical-writing` 和 `$rd-detailed-design` 的多维度检查中。

## AI 系统约束

### LLM 系统
- 区分模型能力、系统能力、当前测试表现、生产可用性
- 默认考虑：评估与验收标准、幻觉风险、提示注入防护、降级策略
- **信任域分离**：检索到的外部文本可以"提供信息"，但不能"授权"shell/文件/网络操作。不同来源的文本视为不同信任域

### ML/DL 系统
- 不把训练集表现等同于泛化能力
- 数据质量、分布偏移必须讨论
- 模型评估须说明指标选择依据和基线对比

## 子代理编排

### 调度原则

- **任务隔离**：每个子任务分配独立子代理，防止上下文污染
- **最小权限**：explorer 只读不写；worker 只在范围内改动
- **编排器不做重活**：主代理负责分诊和路由

### 角色路由

| 角色 | 触发场景 |
|------|---------|
| **worker** | 实现任务、文件创建、配置修改 |
| **explorer** | 代码搜索、架构理解、依赖分析（只读） |
| **awaiter** | 构建、测试、部署等长时间命令 |
| **reviewer** | 代码评审、设计评审、规范检查 |

## Gotchas 坑点记录

> **这是长期最有价值的实践之一**——每次 AI 或团队成员犯错时记录失败模式，长期积累成为信噪比最高的工程知识。

### 记录结构

每条 Gotcha 包含四个要素：

```
### YYYY-MM-DD: 简短标题
- **问题**：发生了什么
- **表现**：怎么发现的（错误信息、测试失败、线上故障）
- **修复**：怎么解决的
- **预防**：怎么避免再犯（加入规则/检查清单/自动化）
```

### 管理原则

- **3 次规则**：同一类坑点出现 3 次以上 → 提升为正式规则（写入 AGENTS.md 或对应 Skill）
- **30 天归档**：超过 30 天未再出现的问题 → 移到归档区，减少噪音
- **Skill 关联**：`$rd-code-review` 在评审中发现的典型问题应同步记录为 Gotcha
- **存储位置**：项目根目录 `GOTCHAS.md` 或 AGENTS.md 的附属文件

## 完成与验证

没有验证，不要直接说"完成了"。最终汇报至少区分：

- 已完成
- 已验证
- 未验证
- 技术债 / 临时妥协
- 风险与后续建议

代码任务完成前，优先运行项目已配置的 typecheck、lint、test、build。若项目未配置相关命令，必须明确说明"未发现已配置的验证命令"，不得用"应该可以"替代验证结果。

### 安全底线

- 不硬编码 secrets / token / API keys
- 不跳过输入校验
- 不把未验证的内容说成确定事实
- 不将 demo-only 代码表述为生产可用
- 提交前检查本次 staged changes 中是否包含疑似 secrets、token、私钥、连接串或 `.env` 内容；发现后停止并报告。

## 任务路由

可用 Skill 一览（`rd-` 前缀，独立使用，任意顺序）：

| Skill | 交付物 | 日常工作 |
|-------|--------|---------|
| `$rd-requirements-analysis` | 结构化需求文档 / PRD | 需求分析与设计 |
| `$rd-technical-writing` | 技术方案 / 概要设计 / 建设方案 | 总体设计方案编写 |
| `$rd-detailed-design` | 详细设计文档 | 详细设计方案编写 |
| `$rd-implement` | 可运行代码 | 代码开发 |
| `$rd-code-review` | 代码评审意见（双阶段） | Code Review |
| `$rd-testing` | 测试用例 / 测试报告 | 单元测试 / 系统测试 |
| `$rd-deployment` | 部署操作手册 / 变更记录 | 安装部署 |
| `$rd-doc-review` | 文档评审意见（三模式） | 需求评审 / 方案评审 / 设计评审 |

### 文档编写与评审的对应关系

| 编写 Skill | 评审 Skill | 评审模式 |
|-----------|-----------|---------|
| `$rd-requirements-analysis` → PRD | `$rd-doc-review` | 需求评审模式 |
| `$rd-technical-writing` → 技术方案/建设方案 | `$rd-doc-review` | 方案评审模式 |
| `$rd-detailed-design` → 详细设计 | `$rd-doc-review` | 设计评审模式 |
| `$rd-implement` → 代码 | `$rd-code-review` | 双阶段代码评审 |
