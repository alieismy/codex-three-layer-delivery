# 设计原则

## 交付物驱动

本体系把 agent 工作导向具体交付物：

- 需求文档；
- 可研报告；
- 证据包和来源笔记；
- 技术方案；
- 概要设计和建设方案；
- 详细设计；
- 标准规范草案；
- 评审意见；
- 条款级修改建议。

## 最小必要改动

Agent 的工作范围应足够窄，确保每一行改动都能追溯到用户请求。

避免：

- 任务外重构；
- 无关格式噪音；
- 假设性抽象；
- 任务不需要的新依赖。

## 证据纪律

结论应由当前可获得的最强证据支撑：

1. 被评审文档原文、被引用条款或已批准上游需求；
2. 官方文档、标准、法律法规或 RFC；
3. 系统事实、架构记录或实际行为；
4. 论文或技术报告；
5. 工程实践文章；
6. 明确标注的推断。

标准规范工作不得编造条款、文档状态、发布日期或效力依据。证据不足时，标注“需人工核实”。

当外部事实、标准元数据、文献、政策、市场资料或厂商结论会实质影响下游文档时，应先形成证据包。证据收集支撑可研、技术方案、标准规范和评审，但不是所有任务的强制第一步。

## 安全默认值

公开模板应比个人本地配置更保守：

- 保守 `sandbox` 默认值；
- `full access`（完全访问权限）需要显式选择；
- 不包含真实凭据；
- 不包含私有 relay endpoint（中继端点）；
- 不把未验证的模型或包版本作为默认事实。

## 周期性复核

用于弥补模型局限的规则，应在模型或工具大版本发布后复核。

表达项目固有文档交付纪律的规则应保持稳定，除非项目工作方式发生变化。

## 排除范围

本仓库明确排除编码开发、代码评审、测试编写/执行、部署执行和发布运维操作。建设方案中可以包含部署架构设计，但部署操作手册和运维命令不属于本项目范围。
