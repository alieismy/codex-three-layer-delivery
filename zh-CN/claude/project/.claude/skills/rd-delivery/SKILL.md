# rd-delivery

编排有边界的文档交付任务，但不替代负责生成或评审具体制品的专业 `rd-*` Skill。

## 交付物

- 交付章程或任务摘要
- 制品、依赖和决策关系图
- 包含进入与退出门禁的阶段计划
- 状态与验证记录
- 跨会话或跨代理交接记录

需要持久化交付记录时，读取 [delivery-record.md](references/delivery-record.md)。沿用仓库现有位置和命名约定；没有必要时，不强加新的任务目录或框架。

## 运行规则

- 仅在用户明确要求编排时使用；单一交付物直接路由到对应专业 Skill
- 只选择决策和交付物所需阶段，不得强制串联全部 `rd-*` Skill
- 以当前范围内已识别且仍有效的权威项目制品作为权威事实来源，把聊天视为临时工作上下文
- 明确授权边界：代理可以起草、验证或建议，但只有获授权的干系人可以批准或基线化制品
- 每个阶段只加载最小相关上下文，并在阶段边界刷新
- 区分长期需求与意图、当前架构、任务特定变更设计、决策理由、证据和评审发现等持久制品类型，不得让它们相互静默替代
- 把交付记录作为索引，而不是制品的第二份副本：记录状态和精简决策背景，并链接到完整内容的唯一权威位置

## 工作流

### 1. 界定交付任务

- 明确真实决策或交付目标、受众、范围、排除项、成功标准、决策权限和日期/版本边界
- 检查现有项目指南、文档地图、模板、术语表、基线、上游决策和活动任务记录
- 区分可由仓库回答的事实，以及需要用户决定的范围、优先级、风险和批准事项
- 适合迭代澄清时，每次只询问一个影响最大的未决事项，并给出建议和取舍；仅当等待会实质影响进展时，才批量提出相互独立的问题

**完成标准：** 目标交付物、控制性输入、决策责任人和阻塞性未知项均已明确。

### 2. 建立制品与依赖关系图

每个必要制品应记录：

- 标识、标题、责任人或决策主体、状态和权威来源路径
- 上游输入和下游使用方
- 适用的专业 Skill 与评审模式
- 阻塞性决策、证据、依赖和验证方法

大型任务应按决策闭环切分：每个工作包都应产生可独立评审的结果，能在有边界的工作会话内完成，并声明阻塞关系。不得仅按文档章节切分而产生不可验证的碎片。

建立关系图时区分三种状态：

- **可定义：** 产出和完成条件足够精确，可以形成工作包
- **尚未明确：** 事项在范围内，但必须先解决相关决策或证据，才能精确定义
- **范围外：** 事项超出交付目标，除非明确变更范围，否则不会成为可执行工作

只有完成条件和阻塞关系足够精确时，才能把事项从“尚未明确”提升为工作包。范围外事项应单独保留，防止其静默进入可执行工作范围。

**完成标准：** 每个计划制品均有用途、责任人、状态、前置条件、退出门禁和下游交接；其他已知重要事项均明确归入尚未明确或范围外。

### 3. 执行必要阶段

将工作路由到最匹配的 Skill：

| 需要 | Skill |
|------|-------|
| PRD、SRS 或结构化需求 | `rd-requirement` |
| 面向决策的可行性判断 | `rd-feasibility` |
| 外部、当前、争议或仓库证据 | `rd-research` |
| 方案选择与高层架构 | `rd-solution` |
| 可实施契约与详细设计 | `rd-design` |
| 规范性条款或标准工作 | `rd-specification` |
| 面向受众的专业成稿 | `rd-writing` |
| 独立问题与结论 | `rd-review` |

每个阶段开始前加载作为权威依据的上游制品和适用的范围规则。每个阶段结束后记录产出、变更的决策、未决事项、已执行验证和下一批可开始的工作包。

**完成标准：** 每个产出均满足对应专业 Skill 的质量门禁并标明状态；下游不得把未标识的草稿当作已批准基线。

### 4. 在阶段边界验证

- 检查需求与决策追踪、术语、版本、证据边界和制品一致性
- 将每个门禁标明为机器检查或人工决策。机器检查必须有可复验证据；人工决策必须记录明确的决策人、结论、日期和条件
- 需要独立结论时使用 `rd-review`；作者自检不能代替独立评审
- 下游证据与上游决策冲突时，重新打开上游决策，不得静默修补后续文档；上游发生实质变更后，受影响的下游批准或评审在重新执行前失效
- 只有获授权的决策责任人才能豁免门禁，并记录理由、有限范围、剩余风险和重新评审触发条件
- 门禁失败时返回最近的受影响工作包或决策，不重启无关阶段；连续无法解决的失败应转为明确阻塞项
- 实质变更后重新执行受影响的检查，并记录仍未验证的内容

**完成标准：** 阶段退出决定依据明确的证据、问题、决策权限和未决风险规则形成。

### 5. 关闭或交接

- 汇总已完成、已验证、有条件接受、已阻塞、已替代和未验证的制品
- 记录决策的理由、备选项、后果和决策主体；仅当决策难以逆转、脱离上下文会令人困惑且存在真实取舍时创建 ADR
- 只把稳定、已评审的约定或决策提升为持久项目指南；临时笔记和会话日志不得写入 `AGENTS.md`
- 给出下一批可执行工作：阻塞项已解除的工作包、需要责任人作出的决策和准确验证动作
- 交接材料应隐藏密钥及非必要的个人或基础设施标识；敏感原始证据使用受控指针，不复制到会话记录

**完成标准：** 后续评审者或未来会话无需从聊天中重建实质上下文，也无需协调相互重复的决策记录，即可依据仓库制品继续工作。

## 质量门禁

- [ ] 用户已明确要求编排，且该 Skill 没有替代单一专业 Skill
- [ ] 目标、范围、决策权限、成功标准和日期/版本边界明确
- [ ] 制品状态、权威来源路径、依赖和阻塞关系为当前状态
- [ ] 可定义、尚未明确和范围外的工作保持区分
- [ ] 只选择了必要阶段
- [ ] 每个阶段都有可检查的进入和退出条件
- [ ] 机器检查、人工决策和授权豁免已经区分并留有证据
- [ ] 草稿、评审中、已批准、已基线化、已替代和已阻塞状态没有混淆
- [ ] 权威指针指向当前范围内的有效制品；过期、缺失或越界路径已报告而未被继续采用
- [ ] 重要决策、证据缺口、验证结果和后续动作已持久化且可追踪
- [ ] 完整制品或决策内容只有一个权威位置；交付记录以指针引用而不重复维护
- [ ] 交接内容无需依赖隐藏聊天历史即可理解
- [ ] 交接不含密钥或非必要敏感标识，需要时安全指向受控证据

## 范围外

- 现有项目约定已足够时，不另建平行仓库框架
- 小型或单文档任务不强制执行 PRD 到设计的流水线
- 证据或授权不足时，不宣称干系人已批准、文章已发布、系统已部署或运行成功
- 不实现代码，不执行部署操作，不管理生产变更
