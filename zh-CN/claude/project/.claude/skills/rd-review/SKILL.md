# $rd-review

对需求、可研、方案、设计和标准规范文档进行**结构化评审**，产出分级问题和可执行修改建议。

## 适用文档类型

| 模式 | 评审对象 | 上游 Skill |
|------|---------|-----------|
| **需求评审** | PRD / SRS / 需求文档 | `$rd-requirement` |
| **可研评审** | 可研报告 / 可行性分析报告 | `$rd-feasibility` |
| **方案评审** | 技术方案 / 概要设计 / 建设方案 | `$rd-solution` |
| **设计评审** | 详细设计文档 | `$rd-design` |
| **标准评审** | 标准 / 规范 / 指南 / 条款草案 | `$rd-specification` |

## 交付物

- 结构化评审报告（分级问题清单 + 改进建议）
- 评审结论（通过 / 有条件通过 / 不通过）
- 可选：条款级或章节级修改建议表

---

## 通用评审框架

所有文档类型共享的评审方法论：

### 1. 评审范围确认

- 明确评审对象和版本
- 确认评审维度（全面 / 聚焦特定维度）
- 获取相关上下文（上游文档、约束条件）
- 保留被评审文档意图，不静默改写范围或业务决策

### 2. 隐含假设挖掘

- 识别文档中的**隐含假设**
- 对每个假设判断：已验证 / 合理但未验证 / 存疑
- 存疑假设列为风险项

### 3. 反驳优先

- **先假设文档有问题**，找出最可能的薄弱环节
- 再做支持性分析
- 最终给出综合判断和置信度

### 4. 问题分级

| 级别 | 含义 | 要求 |
|------|------|------|
| **Blocker** | 根本性缺陷，不可按此推进 | 必须重写/重新设计 |
| **Critical** | 重大遗漏或错误 | 必须修改后再推进 |
| **Major** | 显著改进空间 | 应当修改 |
| **Minor** | 建议优化 | 可选 |

每条问题应包含：

- 位置：章节、条款、表、图或段落
- 问题：错在哪里或缺什么
- 依据：原文、上游需求、标准或推理
- 影响：为什么重要
- 建议：具体修改文本或下一步动作

### 5. 评审结论

| 结论 | 条件 |
|------|------|
| **通过** | 无 Blocker/Critical，Major ≤ 2 且有明确修复计划 |
| **有条件通过** | 无 Blocker，Critical 有明确修复方案 |
| **不通过** | 存在 Blocker，或 Critical 过多 |

## 模式一：需求评审

评审 `$rd-requirement` 产出的 PRD / SRS / 需求文档。

### 评审维度

| 维度 | 检查要点 |
|------|---------|
| **完整性** | P0 需求是否全覆盖；功能/非功能/约束/假设/排除项是否齐全 |
| **可验证性** | 每项功能需求是否有可执行的验收标准（Given/When/Then） |
| **一致性** | 需求间有无矛盾；术语是否统一 |
| **优先级合理性** | P0/P1/P2 划分是否合理；是否存在 P0 过多的"全是重点"问题 |
| **可行性** | 是否有明显不可实现或高风险需求未标注 |
| **边界清晰度** | 排除项是否明确；接口边界是否清楚 |
| **用户视角** | 是否从用户/业务角度出发而非技术角度 |

### 常见问题模式

- 需求描述过于笼统（"系统应高性能"）→ 要求量化
- 验收标准缺失或不可执行
- 隐含的非功能需求未显式化
- 需求间存在隐性依赖未标注

## 模式二：可研评审

评审 `$rd-feasibility` 产出的可研报告 / 可行性分析报告。

### 评审维度

| 维度 | 检查要点 |
|------|---------|
| **决策清晰度** | 可行性问题是否明确；结论是否清楚 |
| **证据质量** | 事实、估算、假设、未知项是否区分 |
| **维度覆盖** | 技术、经济、进度、运行、合规、风险是否覆盖 |
| **方案比较** | 是否比较可行替代方案，必要时是否包含现状基线 |
| **成本与进度依据** | 数字是否有来源、估算依据或假设标注 |
| **风险处理** | 阻塞点、推进条件、缓解和核验动作是否明确 |
| **结论纪律** | 结论是否由分析推导，而非偏好先行 |

### 常见问题模式

- 直接给“可行”但缺少条件和依据
- 成本或周期数字没有来源或估算依据
- 忽略维持现状作为基线方案
- 只列风险，不给缓解或核验动作

## 模式三：方案评审

评审 `$rd-solution` 产出的技术方案 / 概要设计 / 建设方案。

### 评审维度

| 维度 | 检查要点 |
|------|---------|
| **需求覆盖** | P0/P1 需求是否全部覆盖；是否有需求被遗漏或曲解 |
| **候选方案充分性** | 是否有 ≥2 个候选方案；比较是否客观公正 |
| **架构合理性** | 组件划分、职责分离、耦合度、通信方式 |
| **可扩展性** | 水平/垂直扩展路径；容量规划是否合理 |
| **可靠性** | 单点故障分析；容灾策略；数据一致性 |
| **安全性** | 认证授权、数据保护、接口安全 |
| **部署架构**（建设方案） | 基础设施拓扑、设计层面的部署策略、环境规划、容量预估 |
| **成本** | 开发/运维/许可成本估算是否合理 |
| **风险** | 风险识别是否充分；缓解措施是否可行 |
| **退出路径** | 方案验证失败或被否决时是否有替代路径 |

### 常见问题模式

- 只给"唯一最优方案"，无对比
- 性能数字无来源标注（编造基准）
- 忽略运维复杂度
- 建设方案缺少部署架构和环境规划

## 模式四：设计评审

评审 `$rd-design` 产出的详细设计文档。

### 评审维度

| 维度 | 检查要点 |
|------|---------|
| **接口完备性** | 入参/出参/错误码/幂等性是否完整；版本策略是否明确 |
| **数据模型** | ER 设计合理性；字段完备性；索引设计；范式/反范式理由 |
| **流程正确性** | 核心流程是否覆盖正常/异常/超时路径 |
| **并发控制** | 锁策略、乐观/悲观选择、竞态条件分析 |
| **幂等设计** | 需要幂等的操作是否有保证机制 |
| **安全设计** | 认证、授权、输入校验、数据保护 |
| **错误处理** | 错误分类、传播策略、降级路径 |
| **可实现性** | 设计是否考虑了实际技术栈的约束和能力 |
| **可验证性** | 评审方能否对照需求、约束和标准验证设计 |

### 常见问题模式

- 接口定义缺错误码
- 并发场景未分析
- 错误处理只考虑"正常失败"，忽略超时和部分成功
- 数据模型反范式无性能理由支撑
- 设计留"待定"但无 owner 和截止时间

## 模式五：标准评审

评审 `$rd-specification` 起草或修订的标准、规范、指南或条款草案。

### 评审维度

| 维度 | 检查要点 |
|------|---------|
| **效力与范围** | 文档类型、适用范围、效力边界是否明确 |
| **条款正确性** | 条款是否技术正确，是否与引用文件一致 |
| **规范性清晰度** | 强制性、推荐性、资料性内容是否清晰分离 |
| **可验证性** | 要求是否可测试、可检查或可审计 |
| **术语一致性** | 术语、缩略语、符号、表、图是否一致 |
| **引用完整性** | 规范性引用是否准确、必要、实际使用 |
| **冲突识别** | 是否识别内部矛盾或与上游标准冲突 |

### 常见问题模式

- 使用“支持”“优化”“提升”等无判据动词写强制性条款
- 引用标准但未核实题名、状态、条款或适用性
- 将资料性背景和可执行要求混写
- 加入超出标准范围的实现细节

## 规范注入检查

执行前检查：
- 项目是否有评审规范或 checklist 模板
- 已有的架构决策记录（ADR）
- 已通过评审的同类文档（作为基线参考）
- 标准类任务需检查术语表、规范性引用、条款编号和意见表格式

## MCP 工具使用

- **DeepWiki**：查询类似系统的架构设计参考
- **Sequential Thinking**：复杂权衡推理和多方案对比
- **Context7**：核实技术选型的可行性
- **web_search / Tavily / Brave Search**：核实标准、政策、市场事实或技术可行性

## 质量门禁

交付前核查：

- [ ] 已根据文档类型选择正确的评审模式
- [ ] 隐含假设已识别和分类
- [ ] 反驳分析已完成（先找问题，再找优点）
- [ ] 每条问题有严重级别和具体改进建议
- [ ] 评审结论明确（通过 / 有条件通过 / 不通过）
- [ ] Blocker/Critical 问题有行动项建议
- [ ] 标准或外部事实结论已引用、已核实，或明确标注需要人工核实

## 不做

- 不做"挑刺式"评审——每条意见必须有建设性建议
- 不在评审中重新做设计——评审是评估，不是替代
- 不因评审人偏好推翻有据可依的决策
- 不只说"总体不错"——必须给出结构化评审
- 不编造标准条款、来源依据或文档状态
