# B1 — 同一词跨三个契约

SYNTHETIC（合成）案例，依据仓库区分文档处理与审批权限的规则构造。API、记录、数值均为虚构。以下摘录对比较的术语和行为是完整的。

## R1 — 已批准产品需求，req-r2

评审请求被队列持久接收后，应在2秒内返回回执；回执不表示责任人批准。具名且获授权的文档责任人查看相关证据后决定批准。责任人离线时，请求提交仍可使用。现有客户端将 Boolean 字段 `accepted` 解释为“队列已持久接收请求”，本次发布保留该公共响应字段。

## D1 — 当前设计，design-r3，评审中

队列确认持久收件后，POST /reviews 返回 `{accepted: true, request_id: ...}`。正文称：“accepted 的请求进入已批准文档状态，调用方可把 accepted=true 当作发布权限。”状态列表用 `accepted` 同时指队列收件和责任人批准，没有定义持久化的是哪种状态。D1 没有描述后续责任人批准事件。已批准需求没有规定发布 API，也未授权自动发布。

## T1 — 既有验收检查表，test-r1

一次合成队列 stub 演练在0.7秒内返回回执，检查表将该行为对2秒回执需求标为 PASS。另一行因为观察到 `accepted=true`，将“责任人批准及发布权限”标为 PASS；演练中没有人类批准或发布动作。

## M1 — 本次维护范围

责任人要求评审上述三个契约摘录，提出最小措辞/接口澄清，保留已批准行为及现有客户端兼容性。不要求实现、改变规范性需求或执行新测试。缺失的契约决策可以指派责任人处理，同时继续完成证据支持的独立修正。
