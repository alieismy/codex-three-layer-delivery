# CLAUDE.md - 项目文档交付纪律（v4）

本文件定义 Claude Code 在系统设计、架构设计、可研、标准规范和文档评审工作中的项目级约束。`rd-*` Skills 可独立使用、任意顺序执行，不强制流水线。

本适配包明确排除编码开发、代码评审、测试编写/执行、部署执行和发布运维操作。

## 写作前评估

- 当假设会影响需求、可研、设计、标准或评审结论时，必须显式说明。
- 如果多种理解会影响范围、成本、合规或架构，列出选项并请用户选择。
- 先读目标文档，再读上游需求、可研报告、技术方案、标准、术语表、评审意见和约束。
- 结构化前保留原始文本；不得静默改写用户意图、条款原文或干系人决策。

## 范围锁定

- 优先采用满足任务的最小文档改动。
- 复用既有模板、术语、编号、评审表和文档结构。
- 不增加无必要章节、框架或流程负担，除非能提升可追溯性、可评审性或决策质量。
- 每一行改动都应能追溯到用户请求或必要的一致性同步。

## 目标驱动执行

| 请求 | 可验证目标 |
|---|---|
| 分析需求 | 产出含优先级、假设、排除项、验收标准的 PRD/SRS 条目 |
| 评估可行性 | 给出可行 / 有条件可行 / 不可行，并说明依据、条件和风险 |
| 写方案 | 比较候选方案并证明推荐方案 |
| 写详细设计 | 明确接口、数据、流程、错误、安全和未决决策 |
| 写专业文章或简报 | 面向受众组织主张、证据、反方论证和有边界结论 |
| 评审文档 | 产出分级问题，包含依据、影响和建议 |
| 评审标准 | 引用具体条款，必要时提供规范性替换文本 |

运行验证命令前，先检查项目已有入口，如 `scripts/`、`package.json`、`Makefile`、`justfile` 或文档专用工具。

## 何时执行 / 何时确认

| 判断 | 行为 |
|---|---|
| 指令明确且改动可控 | 直接执行 |
| 多种文档结构或方案路径影响不同 | 给出推荐和理由，再请用户选择 |
| 模糊点影响范围、成本、合规、风险或架构 | 复述理解并提问 |
| 操作具有破坏性或会改变权威基线 | 先确认 |
| 事实或标准依据无法核实 | 说明已知事实和核验缺口 |
| 研究涉及不确定或易漂移事实 | 先搜索核实 |

## Claude Code 文件映射

| 范围 | Claude Code 文件 |
|---|---|
| 用户级 memory（记忆）和行为规则 | `~/.claude/CLAUDE.md` |
| 项目级 memory（记忆）和行为规则 | `{project}/CLAUDE.md` |
| 项目设置 | `{project}/.claude/settings.json` |
| 项目级 Skills | `{project}/.claude/skills/rd-*/SKILL.md` |
| 项目命令（如后续添加） | `{project}/.claude/commands/*.md` |

不要把 Codex-only 的 `config.toml`、Codex hooks 或 Cursor `.mdc` 语法直接粘贴到 Claude Code 文件中；应翻译为 Claude Code 原生载体。

## 规范注入

执行文档交付 Skill 前：

1. 检查本 `CLAUDE.md` 的文档约定。
2. 检查既有模板、术语表、命名规则、评审表和已批准样例。
3. 检查上游决策、需求、可研结论、标准引用和架构约束。
4. 将长期有效的决策沉淀到 `CLAUDE.md` 或链接的项目文档，不只留在聊天记录。

`CLAUDE.md` 面向 agent，记录稳定文档交付约束、目录约定、风险点和验证命令。`README.md` 面向人类，说明项目是什么、为什么存在、如何开始。

## 证据纪律

- 能从目标文档确认的事实，优先引用目标文档。
- 能从官方文档、标准、法律法规、RFC 或论文确认的事实，优先查原始来源。
- 区分事实、假设、估算、推断和未决问题。
- 区分文档声明、源码实现、静态配置、最终生成或实际生效配置、运行状态、业务或生产验收。只报告实际达到的最高状态，不能用较低状态证明较高状态。
- 有充分依据的“无需修改”属于有效结论；证据支持保持现状时，不得强行提出修改。
- 标准规范工作不得编造条款、状态、发布日期或效力依据。证据缺失时标注需人工核实。

## MCP 与工具路由

外部工具只服务具体证据需求：

- 库、框架、SDK 文档：官方文档；已配置时可用 Context7。
- 当前 Web 研究：对时效事实使用 web search。
- 开源架构参考：按需使用 DeepWiki。
- 复杂多方案推理：优先模型推理；按需使用 Sequential Thinking。
- 标准或政策核验：优先标准主管机构、监管机构或厂商官方文档。

## 质量门禁

完成需求、可研、设计、标准或评审工作前，至少确认：

- 关键结论有证据支撑。
- 事实、假设、估算、推断和未知项已区分。
- 相关边界条件、合规约束和风险已覆盖。
- 无法确认的点已列出核验动作。
- 最终输出区分已完成、已验证、未验证、证据限制、风险和后续建议。

## 文档 Skill 路由

| Skill | 交付物 | 日常工作 |
|---|---|---|
| `rd-requirement` | 结构化需求 / PRD / SRS | 需求分析和产品/设计输入 |
| `rd-feasibility` | 可研报告 / 可行性分析报告 | 项目可行性和决策支持 |
| `rd-research` | 证据包 / 研究笔记 / 事实核查矩阵 | 标准、开源、AI 工具、配置行为和争议主张研究 |
| `rd-solution` | 技术方案 / 概要设计 / 建设方案 | 系统架构和方案文档 |
| `rd-design` | 详细设计文档 | 接口、数据、流程、错误、安全和并发设计 |
| `rd-specification` | 标准/规范草案或条款修订 | 标准制定、修订和规范性用语工作 |
| `rd-writing` | 技术文章 / 证据报告 / 决策简报 | 面向受众、有来源支撑的专业写作 |
| `rd-review` | 独立评审意见 | 工程文档、研究报告、标准和文章评审 |
| `rd-delivery` | 交付章程 / 制品地图 / 阶段门禁 / 交接 | 显式编排多阶段和跨会话任务 |

任务匹配触发条件时使用对应专业 Skill，不要强制串成流水线。外部或争议证据使用 `rd-research`，面向受众的成稿使用 `rd-writing`，独立结论使用 `rd-review`。仅当用户明确要求协调多个制品、阶段门禁或持久化交接时，才使用 `rd-delivery`。

使用 `rd-delivery` 时，区分长期需求、当前架构、任务特定变更设计、决策理由、证据和评审发现的权威层级；区分可复验的机器检查与明确的人工决策；记录授权豁免和重新评审触发条件；上游实质变更后使受影响的下游评审失效；拒绝过期、缺失或越出仓库边界的权威指针。

## 安全与 AI 系统设计

安全性是设计质量属性：

- 身份认证与授权模型；
- 数据保护和隐私；
- 输入/数据校验期望；
- 审计与追踪；
- 失效处理和信息泄露边界；
- 合规和标准符合性。

AI/ML 系统需要区分模型能力、系统能力、评估结果和生产可用性。相关时应包含评估设计、幻觉风险、提示注入风险、数据边界和降级策略。

## 完成与验证

没有验证，不要直接说“完成”。最终汇报必须区分：

- 已完成工作；
- 已执行验证；
- 未验证区域；
- 证据限制；
- 风险和后续建议。
