# CLAUDE.md - 项目工程纪律（v4）

本文件定义 Claude Code 项目级工程约束。8 个 `rd-*` Skills 可独立使用、任意顺序执行，不强制流水线。

## 动手前先想清楚

- 明确陈述假设；不确定时先问。
- 如果存在多种理解，列出选项让用户选择。
- 先读目标文件，再读调用方、接口定义、相关测试、配置和数据模型。
- 如果影响多个模块或外部契约，先给出简短实施计划。

## 最小改动原则

- 优先最小必要改动。
- 复用现有模式、目录结构和基础设施。
- 不提前增加抽象层。
- 不顺手改善相邻代码、注释或格式。
- 每一行改动都应能追溯到用户需求。

## 目标驱动执行

将任务转化为可验证目标：

- “加验证” -> 写无效输入测试，然后让测试通过。
- “修 bug” -> 写复现测试，然后让测试通过。
- “重构 X” -> 确保重构前后测试都通过。
- 运行 lint、format、test、build、typecheck 前，先查项目已有脚本入口，如 `scripts/`、`package.json`、`Makefile`、`justfile`、`pyproject.toml`、`uv.lock`。

## 何时直接做 / 何时先问

| 判断 | 行为 |
|---|---|
| 指令明确且改动可控 | 直接做 |
| 多种合理方案影响不同 | 给出推荐和理由，再请用户选择 |
| 需求模糊 | 复述理解，确认后再做 |
| 破坏性操作 | 必须先确认 |
| 可行性不清 | 先说明风险和限制 |
| 需要创建多个新文件或目录 | 先说明计划和文件清单 |
| 研究涉及不确定或易漂移领域 | 先搜索核实，再给结论 |

## Claude Code 文件映射

| 范围 | Claude Code 文件 |
|---|---|
| 用户级 memory 和行为规则 | `~/.claude/CLAUDE.md` |
| 项目级 memory 和行为规则 | `{project}/CLAUDE.md` |
| 项目设置 | `{project}/.claude/settings.json` |
| 项目级 Skills | `{project}/.claude/skills/rd-*/SKILL.md` |
| 项目命令（如后续添加） | `{project}/.claude/commands/*.md` |

不要把 Codex-only 的 `config.toml`、Codex hooks 或 Cursor `.mdc` 语法直接粘贴到 Claude Code 文件中；应翻译为 Claude Code 原生载体。

## 规范注入

项目规范应存储在仓库文件中，保证 Claude Code 在不同会话中加载同一套工程约束。

涉及设计和实现的 Skill 执行前：

1. 检查本 `CLAUDE.md` 中的项目特定约定。
2. 检查已有设计决策或架构约束。
3. 将长期有效的项目决策沉淀到 `CLAUDE.md` 或链接的项目文档，不只留在聊天记录中。

`CLAUDE.md` 面向 agent，记录工程约束、脚本、目录约定、风险点和验证命令。`README.md` 面向人类，说明项目是什么、为什么存在、如何开始。

## 证据纪律

- 能用代码确认的，优先看代码。
- 能用官方文档确认的，优先看官方文档。
- 能用标准、RFC 或论文确认的，优先看原始来源。
- 外部验证不可用时，明确说明限制。
- 区分事实、推断、假设和未解决问题。

## MCP 与工具路由

外部工具只为具体证据或工作流需求启用，不作为宽泛默认值：

- 库、框架、SDK 文档：优先官方文档；已配置时可使用 Context7 等文档 MCP。
- 当前 Web 研究：对时效信息使用 web search。
- 浏览器交互和 E2E 测试：优先项目本地测试脚本或 Playwright。
- 跨仓库代码分析：仅在能明显提高证据质量时使用仓库搜索工具。

## 质量门禁

完成研究、设计、实现或评审任务前，至少确认：

- 关键结论有证据支撑，而不是只基于推断。
- 关键假设已显式标注。
- 失败路径和边界条件已覆盖。
- 无法确认的点已单独列出。
- 验证动作和验证结果已记录。

## R&D Skill 路由

项目 Skills 使用 `rd-` 前缀：

| Skill | 交付物 | 日常工作 |
|---|---|---|
| `rd-requirements-analysis` | 结构化需求文档 / PRD | 需求分析 |
| `rd-technical-writing` | 技术方案 / 概要设计 / 建设方案 | 架构与方案 |
| `rd-detailed-design` | 详细设计文档 | 接口、数据、流程、失败路径 |
| `rd-implement` | 可运行代码和测试 | 代码开发 |
| `rd-code-review` | 代码评审意见 | 代码评审 |
| `rd-testing` | 测试计划、测试或测试报告 | 单元、集成、系统或 E2E 测试 |
| `rd-deployment` | 部署操作手册 / 变更记录 | 发布与回滚计划 |
| `rd-doc-review` | 文档评审意见 | 需求、方案或设计评审 |

当任务匹配 Skill 触发条件时使用对应 Skill。不要强制所有 Skill 串成流水线。

## 代码质量约束

| 约束 | 阈值 |
|---|---:|
| 单个函数或方法 | <= 50 行 |
| 单个文件 | <= 500 行 |
| 嵌套层级 | <= 3 层 |
| 函数参数 | <= 5 个 |

优先可读、直接的代码。注释只用于解释 WHY。

## 安全底线

- 不硬编码 secrets、token、API keys 或私有 relay URL。
- 不提交 `.env`、私钥或本机凭据。
- 外部输入必须校验。
- 错误信息避免泄露内部细节。
- 引入新依赖前确认版本、许可证和已知漏洞。
- 提交前检查 staged changes 是否包含疑似 secrets、token、私钥、连接串和 `.env` 内容。

## 完成与验证

没有验证，不要直接说“完成了”。最终汇报至少区分：

- 已完成工作。
- 验证命令和结果。
- 未验证区域。
- 技术债或临时妥协。
- 风险和后续建议。
