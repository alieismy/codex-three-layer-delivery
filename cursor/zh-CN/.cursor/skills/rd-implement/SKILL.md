# $rd-implement

基于设计产出**可运行、可测试、可部署的代码**。

## 交付物

- 符合设计的实现代码
- 必要的单元测试（与代码同步提交）
- 变更记录（Changelog 条目）

## 核心原则

1. **先想再写**：动手前明确陈述假设和实施计划。有多种方案时先说明理由。
2. **最简优先**：选最简单能满足需求的实现。不为假设性未来需求增加复杂度。
3. **最小改动**：只改必须改的。不顺手重构无关代码。
4. **目标驱动**：把需求转化为可验证目标（"写失败测试 → 让测试通过"）。

## 执行步骤

### 1. 上下文加载

- 读取相关设计文档（`$rd-detailed-design` 产出）
- 读取目标文件、调用方、接口定义、相关测试
- 检查项目规范（`.cursor/rules/` 中的相关规则）
- 确认技术栈版本和依赖约束

### 2. 实施计划

影响多文件或跨模块时，先输出简短实施计划：
- 需修改的文件**完整路径**清单（对抗上下文衰减）
- 修改顺序和依赖关系
- 每步预期结果和验证命令
- 风险点标注

### 3. 编码实现

遵循项目级代码质量阈值：

| 约束 | 阈值 |
|------|------|
| 单个函数/方法 | ≤ 50 行 |
| 单个文件 | ≤ 500 行 |
| 嵌套层级 | ≤ 3 层 |
| 函数参数 | ≤ 5 个 |

编码纪律：
- 优先复用现有模式和基础设施
- 引入新依赖前确认版本、许可证和已知漏洞
- 不硬编码 secrets / token / API keys
- 注释解释 WHY 而非 WHAT
- 不因为"以后可能会扩展"提前增加抽象层

### 4. 同步测试（TDD RED-GREEN-REFACTOR）

推荐使用细粒度 TDD 循环——**每个接口/功能点单独走完一轮再切到下一个**：

1. **RED**：先写一个会失败的测试（明确预期行为）
2. **GREEN**：写最少的代码让测试通过
3. **REFACTOR**：清理冗余，优化结构，确保测试仍通过
4. 切到下一个接口/功能点，重复循环

粒度选择：
- 新功能：每个接口一轮 TDD
- Bug 修复：先写复现测试（RED），再修复（GREEN）
- 重构：确保重构前后测试都通过
- 测试覆盖至少：正常路径 + 核心边界条件

### 5. 验证前置（Verification Before Completion）

**不要直接说"完成了"——先自验证：**

- 运行现有测试套件，确认无回归
- 使用 ReadLints 工具检查编辑过的文件，确认无新 linter 错误
- 确认改动范围与计划一致，无越界
- 对照设计文档检查接口和数据模型是否匹配
- 汇报时区分：已完成 / 已验证 / 未验证 / 技术债

## 规范注入检查

执行前检查：
- `.cursor/rules/` 中的项目编码规范（命名、格式、错误处理）
- Git 提交规范（commit message 格式）
- 已有的架构模式和设计决策
- CI/CD 管道要求

## MCP 工具使用

- **Context7**：查询库/框架 API 用法，不确定时优先查文档而非猜测
- **Sequential Thinking**：复杂算法或并发逻辑的推理
- **Augment Context Engine**：跨仓库代码搜索和模式参考

## 质量门禁

交付前核查：

- [ ] 代码符合设计文档的接口和数据模型
- [ ] 核心功能有单元测试覆盖
- [ ] 无硬编码 secrets
- [ ] 现有测试通过，无回归
- [ ] ReadLints 检查无新错误
- [ ] 改动可追溯到需求或设计
- [ ] 复杂逻辑有注释解释 WHY

## 过度设计判断

- 当前只有 1 个实现 → 不建接口/抽象工厂
- 当前没有变化需求 → 不用策略模式/模板方法
- 消除重复会引入更高复杂度 → 保留适度重复

## 失败回退策略

- **两次失败规则**：同一问题连续两次修复失败 → 建议开新会话 + `git reset --hard`，从干净上下文重新开始
- 原因：连续失败通常意味着上下文已被错误方向污染，继续在同一会话中修复往往越改越偏
- 回退前先将当前分析和失败原因写入 `.cursor/rules/` 规则文件，避免在新会话中重蹈覆辙

## 不做

- 不跳过读代码直接写代码
- 不"顺手"改善相邻代码、注释或格式
- 不删除已有的无关代码（即使看起来是死代码）
- 不引入未被要求的抽象、模式或依赖
