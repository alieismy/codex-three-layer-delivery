# $rd-technical-writing

研究和编写高质量技术文档——**技术方案、概要设计、建设方案、可行性分析、技术白皮书**。

## 交付物

- 技术方案文档 / 概要设计 / 建设方案
- 候选方案比较矩阵
- 推荐方案及风险说明

## 执行步骤

### 1. 目标与约束确认

- 明确文档类型（概要设计 / 建设方案 / 可行性分析）
- 确认读者（决策层 / 技术团队 / 甲方评审）
- 确认约束条件：时间、预算、技术栈、合规要求
- 检查是否有已有需求文档（`$rd-requirements-analysis` 产出）

### 2. 方案研究与候选生成

- 至少生成 **2 个候选方案**，不允许只给"唯一最优"
- 每个方案包含：架构概览、核心组件、技术栈、部署拓扑
- 使用搜索工具核实关键技术选型的可行性和成熟度

### 3. 多维度交叉检查

对每个候选方案从以下维度评估：

| 维度 | 检查内容 |
|------|---------|
| 功能完整性 | 是否覆盖全部 P0/P1 需求 |
| 性能 | 容量规划、瓶颈预判、扩展路径 |
| 可靠性 | 容错、灾备、数据一致性策略 |
| 安全性 | 认证授权、输入校验、数据保护、审计 |
| 可维护性 | 代码组织、监控告警、运维复杂度 |
| 成本 | 开发成本、运维成本、许可费用 |
| 风险 | 技术风险、人员风险、进度风险、外部依赖风险 |
| 回滚 | 方案失败时的退出路径 |

### 4. 推荐与决策建议

- 基于量化或半量化比较给出推荐
- 明确推荐理由和放弃其他方案的理由
- 标注推荐的置信度（高 / 中 / 低）及依据
- 说明遗留风险和后续需确认事项

### 5. 文档结构化输出

根据文档类型选择对应模板：

#### 技术方案 / 概要设计

```
1. 背景与目标
2. 需求概述（引用需求文档）
3. 约束条件
4. 候选方案
   4.1 方案 A
   4.2 方案 B
5. 方案比较
6. 推荐方案
7. 架构设计（推荐方案详述）
8. 关键风险与缓解措施
9. 实施计划（里程碑）
10. 遗留问题
```

#### 建设方案（含部署架构）

```
1. 背景与目标
2. 需求概述
3. 约束条件
4. 候选方案与比较
5. 推荐方案
6. 系统架构设计
7. 部署架构设计
   7.1 基础设施拓扑（网络、计算、存储）
   7.2 环境规划（开发/测试/预发布/生产）
   7.3 部署策略（滚动/蓝绿/金丝雀）
   7.4 容量规划与资源预估
   7.5 高可用与灾备设计
8. 安全设计
9. 关键风险与缓解措施
10. 实施计划与里程碑
11. 遗留问题
```

> **与 `$rd-deployment` 的边界**：建设方案定义部署的*设计*（拓扑、策略、环境规划）；`$rd-deployment` 负责部署的*执行*（操作手册、脚本、回滚验证、变更记录）。

## 规范注入检查

执行前检查：
- `.cursor/rules/` 中是否有技术方案模板或格式要求
- 是否有架构决策记录（ADR）的规范
- 已有的技术栈约束和选型原则

## MCP 工具使用

- **Context7**：查询技术栈/框架官方文档和最佳实践
- **DeepWiki**：分析参考项目的架构设计
- **Sequential Thinking**：复杂多方案对比推理
- **Tavily / Brave Search**：技术选型可行性核实、行业案例检索

## 质量门禁

交付前核查：

- [ ] 候选方案 ≥ 2 个，比较充分
- [ ] 推荐依据明确，置信度已标注
- [ ] 安全性维度已覆盖（认证、校验、保护、审计）
- [ ] 风险已识别，每项风险有缓解措施
- [ ] 回滚/退出路径已说明
- [ ] 关键数据有来源标注，推断与事实已区分
- [ ] 文档结构完整，读者可独立理解

## 不做

- 不只给一个方案说"这是最优解"
- 不编造基准测试数据或性能数字
- 不把推断说成已验证事实
