# $rd-code-review

对代码实现进行**双阶段结构化评审**，产出分级评审意见。

## 交付物

- 结构化评审报告（分级问题清单）
- 改进建议（每条附具体修改建议）

## 双阶段评审流程

### 阶段一：合规性检查（Gate Review）

快速检查是否满足基本门槛，不通过则直接打回：

| 检查项 | 标准 |
|--------|------|
| 设计对齐 | 实现是否符合详细设计文档 |
| 接口契约 | 接口签名、入参/出参/错误码是否匹配 |
| 测试存在性 | 新功能/修复是否附带测试 |
| 安全底线 | 无硬编码 secrets、无跳过输入校验、无 SQL 拼接 |
| 构建通过 | CI 是否绿灯 |

**如果任一项不通过，直接打回并说明原因，不进入阶段二。**

### 阶段二：代码质量深度评审

通过阶段一后，从以下维度深入检查：

#### 2.1 正确性
- 逻辑是否正确，边界条件是否处理
- 并发安全性（竞态条件、死锁风险）
- 错误处理是否完整（可恢复/不可恢复/降级路径）

#### 2.2 可维护性与代码异味

命名与组织：
- 命名是否清晰、自解释
- 代码组织是否合理（单一职责、关注分离）
- 复杂逻辑是否有 WHY 注释

代码异味识别清单：

| 异味 | 判断标准 | 建议 |
|------|---------|------|
| 重复代码 | 相同逻辑出现 3+ 处 | 提取方法/组件 |
| 过长函数 | > 50 行 | 拆分函数 |
| 过大类/文件 | > 500 行 | 分解模块 |
| 过长参数列表 | > 5 个参数 | 引入参数对象 |
| 发散式变化 | 一个改动要改多处不相关代码 | 重新组织职责 |
| 数据泥团 | 同一组参数反复出现 | 提取数据类 |
| 过度嵌套 | > 3 层嵌套 | 提前返回 / 提取方法 |
| 魔法数字 | 未命名的字面量 | 提取常量 |

#### 2.3 性能
- 是否存在明显性能问题（N+1 查询、不必要的全表扫描、内存泄漏风险）
- 算法复杂度是否合理

#### 2.4 安全性
- 输入校验是否充分
- 认证授权逻辑是否正确
- 敏感数据处理是否符合要求

#### 2.5 测试质量
- 测试是否覆盖正常/异常/边界路径
- 测试是否有断言（非只打印）
- 测试是否独立、可重复

## 问题分级

每条评审意见标注严重级别：

| 级别 | 含义 | 要求 |
|------|------|------|
| **Critical** | 阻塞合入，可能造成故障 | 必须修复 |
| **Major** | 显著质量问题 | 应当修复 |
| **Minor** | 改善建议 | 建议修复 |
| **Nit** | 风格/偏好 | 可选 |

## 规范注入检查

执行前检查：
- `.cursor/rules/` 中的项目编码规范和 code style 配置
- 已有的 code review checklist
- 分支合并策略和 PR 规范

## MCP 工具使用

- **Augment Context Engine**：跨文件和跨仓库的代码追踪
- **Context7**：核实 API 用法是否符合最新文档

## 质量门禁

交付前核查：

- [ ] 阶段一 5 项检查全部执行
- [ ] 每条问题有严重级别和具体修改建议
- [ ] Critical/Major 问题有代码行号定位
- [ ] 已区分"必须修"和"建议改"
- [ ] 评审覆盖全部变更文件

## Gotchas 收集

代码评审是发现坑点的最佳时机。评审完成后：

- 如果发现**反复出现的错误模式**（如多次遗漏分页参数、忽略并发处理），记录为 Gotcha
- 记录格式：问题 / 表现 / 修复 / 预防（详见 `.cursor/rules/08-gotchas-verification.mdc`）
- 同一类问题出现 3 次以上 → 建议提升为编码规范或自动化检查

## 不做

- 不只说"LGTM"或"looks good"——必须给出结构化评审
- 不重写代码替代评审意见——给出修改建议让作者自行修改
- 不在代码评审中发起架构层面的重新讨论（应转到 `$rd-doc-review`）
