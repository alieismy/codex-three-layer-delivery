## 1. 需求分析（`$rd-requirements-analysis`）

### 模板 A：从零开始的需求分析

```
使用 $rd-requirements-analysis

## 背景
{项目/产品背景，1-3 句话}

## 用户原始需求
{用户的原始描述，保留原文不修改}

## 已知约束
- 技术栈：{如 Java/Spring Boot、Python/FastAPI、React 等，或"待定"}
- 目标用户：{如 B 端运维人员、C 端消费者}
- 时间约束：{如 Q3 交付、2 个月}
- 预算/资源约束：{如有}

## 期望产出
{PRD / SRS / 用户故事集，选一个或多个}
```

### 模板 B：已有需求文档的补充分析

```
使用 $rd-requirements-analysis

请基于以下已有需求材料进行结构化分析，补充缺失的维度（非功能需求、约束、假设、排除项、验收标准）：

## 已有材料
{粘贴或引用已有的需求描述/会议纪要/用户反馈}

## 需要重点关注
- {如：性能要求不明确、边界场景未定义、第三方集成范围不清}
```

### 模板 C：快速版（明确指令）

```
使用 $rd-requirements-analysis，将以下需求结构化为 PRD，标注优先级和验收标准：

{直接粘贴用户需求原文}
```

## 3. 技术方案 / 概要设计（`$rd-technical-writing`）

### 模板 A：技术方案

```
使用 $rd-technical-writing

## 文档类型
技术方案 / 概要设计

## 需求来源
{引用 PRD 文档路径或关键需求摘要}

## 目标读者
{决策层 / 技术团队 / 甲方评审}

## 已知约束
- 技术栈：{如 必须使用 Java 17+、PostgreSQL}
- 部署环境：{如 K8s 集群、私有化部署}
- 性能要求：{如 P99 < 200ms、日活 10 万}
- 安全/合规：{如 等保三级、GDPR}
- 预算：{如 年度云资源预算 50 万}

## 特别关注
- {如：需要与现有系统 X 集成}
- {如：需要考虑数据迁移方案}
- {如：请重点对比微服务 vs 单体架构}
```

### 模板 B：可行性分析

```
使用 $rd-technical-writing

## 文档类型
可行性分析

## 分析目标
{一句话说明要验证什么是否可行}

## 需求来源
{引用 PRD 或业务方提出的方向性需求}

## 需要评估的维度
- 技术可行性：{如 现有技术栈能否支撑、是否需要引入新技术}
- 成本可行性：{如 开发周期、运维成本、许可费用}
- 风险评估：{如 团队技能匹配度、外部依赖稳定性}

## 已知约束
- {如：必须在现有架构上扩展，不允许推倒重建}
- {如：团队没有 Rust 经验}
- {如：预算上限 30 万}

## 期望结论
明确给出 可行 / 有条件可行 / 不可行 的结论，附理由和置信度。
```

### 模板 C：快速版

```
使用 $rd-technical-writing，编写技术方案。

需求：{一句话描述核心需求}
约束：技术栈 {X}，部署在 {Y}，性能要求 {Z}。
请至少给出 2 个候选方案并比较。
```

## 组合使用示例

### 示例：完整的需求到上线流程

> **注意**：每一步建议在独立的 Cursor 会话/对话中执行。上一步的产出文档作为下一步的输入引用。
> 对于小功能，可以在同一会话中连续执行多个步骤。

```
# 第 1 步：需求分析（新会话）
使用 $rd-requirements-analysis
背景：公司需要一个内部工单系统，替换现有的邮件审批流程。
用户原始需求：（粘贴原文）
约束：技术栈 Java/Spring Boot，部署在公司 K8s 集群，2 个月交付。

# 第 2 步：需求评审（新会话）
使用 $rd-doc-review，需求评审模式
评审上一步产出的 PRD，重点检查验收标准和优先级。

# 第 3 步：技术方案（新会话）
使用 $rd-technical-writing
基于 PRD 编写技术方案，技术栈限定 Java 17 + Spring Boot 3.x + PostgreSQL。
请比较单体 vs 微服务方案。

# 第 4 步：方案评审（新会话）
使用 $rd-doc-review，方案评审模式
评审技术方案，重点关注架构选型和风险。

# 第 5 步：详细设计（新会话）
使用 $rd-detailed-design
基于技术方案，为工单模块做详细设计，包含接口、数据模型、状态机。

# 第 6 步：设计评审（新会话）
使用 $rd-doc-review，设计评审模式
评审详细设计，重点关注接口幂等性和并发控制。

# 第 7 步：代码实现（新会话）
使用 $rd-implement
基于详细设计实现工单 CRUD + 状态流转。
验收标准：POST 创建工单 → 审批 → 完成，全流程可跑通。

# 第 8 步：代码评审（新会话）
使用 $rd-code-review
评审实现代码，重点关注安全性和错误处理。

# 第 9 步：测试（新会话）
使用 $rd-testing
为工单模块编写单元测试和集成测试，覆盖状态机全部转换路径。

# 第 10 步：部署（新会话）
使用 $rd-deployment
部署工单系统 v1.0 到测试环境，含数据库初始化。
```

## 提示词使用技巧

| 技巧 | 说明 |
|------|------|
| **指令明确时用快速版** | 任务简单清晰，直接用一句话模板，AI 进入快速模式 |
| **复杂任务用完整版** | 多约束、多模块、有历史包袱时，提供完整上下文 |
| **评审时指定重点** | "评审重点"字段能引导 AI 聚焦关键维度，避免泛泛而谈 |
| **引用上游文档** | 用 `@文件路径` 引用上游产出（如 PRD → 技术方案 → 详细设计），Cursor 会自动加载文件上下文 |
| **验收标准要具体** | "能跑通"不如"POST /api/orders 返回 201 + 订单 ID"，越具体 AI 越准确 |
| **分步执行 vs 一次性** | 复杂项目建议每个 Skill 在独立会话中执行；小功能可在同一会话中连续调用 |
| **触发深度分析** | 在提示词中加入"详细分析"或"深入评估"触发 AI 的深度模式，获得多维度分析 |
| **已有代码库先描述上下文** | 修改已有项目时，在提示词中简述项目结构和现有模式，AI 才能复用而非重建 |
| **利用 Cursor @ 引用** | 用 `@文件名` 直接引用项目文件，比粘贴内容更高效且保持上下文完整 |
